The problem

Three ports, three download steps, model names in your code

A local-first app usually ends up juggling a chat server, an embedding server and a speech model — and hard-coding every model name.

Before

  • Ollama on :11434, embeddings on :8000, speech on :9000
  • A different download step, start command and RAM profile per model
  • model="qwen2.5:3b" sprinkled through the codebase
  • Swapping a model breaks the app that called it
  • One model crashing takes the whole stack down

After

  • One gateway on 127.0.0.1:10000 for every role
  • omni init pulls, warms and supervises everything
  • Your app calls chat, embed, tts
  • Config maps role → model, so swapping never breaks an app
  • Each role runs in its own process and restarts itself

Architecture

One port in. Seven roles out.

Engines are never exposed. The gateway routes by path, workers talk over Unix sockets, and only Ollama touches TCP.

Roles

Seven roles, one consistent API

Each role has one endpoint, one default model and one engine — and you can swap any of them without touching your app.

chat

Ollama

Streaming chat completions, optionally with image input when the model has vision.

POST /v1/chat/completions

default · qwen2.5:0.5b

decide

Ollama

Yes/no, choice and score questions scored from one token's logprobs — no text to parse.

POST /v1/systemone

default · OneJev1.5-0.8B

embed

Ollama

Query and document embeddings with task prompts added server-side, warm in 30 ms.

POST /v1/embeddings

default · embeddinggemma-2:270m

image

diffusers

Text-to-image on Metal with steps, seed and size — returned as base64 PNG.

POST /v1/images/generations

default · Qwen-Image-2.1-Turbo

video

ltx-2-mlx

Text-to-video as a queued job: create, poll, download the mp4.

POST /v1/videos

default · LTX-2.3 MLX

stt

parakeet-mlx

Transcribe a recording or an uploaded file, with segment timings.

POST /v1/audio/transcriptions

default · parakeet-tdt-0.6b-v3

tts

mlx-audio

Speech from text with 27 voices and speed control — about 12× realtime.

POST /v1/audio/speech

default · Kokoro-82M

health

gateway

Every worker's status and the model it has loaded, plus the model list.

GET /health · /v1/models

Playground

A workbench for every endpoint

omni ships a browser playground at /. Every tab is a workbench with a UI view, a raw JSON view and a copyable cURL for the exact request it sends.

  • Chat — streaming replies with a live token rate; attach images when the model supports vision.
  • Decide — yes/no, choice and score questions with probability bars.
  • Image & Video — prompts, sizes, steps, seeds; PNG download and mp4 playback.
  • Models — install from Ollama or Hugging Face, switch defaults, watch memory.
  • Embed — rank documents against a query by cosine similarity.
  • STT & TTS — record from the mic, round-trip audio back through speech-to-text.
  • Health — every worker, its status and the model it has loaded.

Features

The parts that usually bite you

Every one of these shipped, with the failure mode it removes.

Decide without generation

Questions are scored from one token's logprobs, so you get calibrated probabilities per option instead of text to parse.

Keep-warm pins

Pin a role and its model stays loaded across restarts. Unpinned models unload after ten idle minutes.

Three views, one request

Every playground tab shows the UI call, the raw JSON and a copyable cURL — the same body, three ways.

Find & install

Search Hugging Face and Ollama per role, filtered to what that role's runtime can actually run, with live download progress.

Self-healing workers

Per-worker locks, exponential-backoff restarts, pid and argv checks — a recycled pid is never signalled.

One error shape

Gateway, workers, routing 404s and validation 422s all answer {"error": {"message", "type"}}.

Hardened local surface

8 MB body caps, finite upstream timeouts, loopback only. A non-loopback host is refused unless you force it.

Survives a closed tab

Requests are retained server-side, so closing the browser never cancels the work — reopen it and the result is there.

Quickstart

Running in three commands

Install the CLI, pull the models, start the gateway.

  1. 1

    Install the CLI

    The script brings Python and uv if they are missing, then installs the omni command.

    shell
    curl -fsSL https://raw.githubusercontent.com/nvkudva/omni-api/main/install.sh | sh

# or, with Homebrew on macOS
brew tap nvkudva/omni
brew install omni
  2. 2

    Pull the models

    omni init validates your config, installs Ollama if it is missing and fetches the chat, decide and embed models, then downloads and starts speech-to-text and text-to-speech. Add --media for image and video too.

    shell
    omni init          # validate, install Ollama, pull the core models, start stt and tts
omni init --media  # also load image and video now
  3. 3

    Start it and open the playground

    omni up runs the gateway and every worker in the background. Then open http://127.0.0.1:10000/.

    shell
    omni up      # gateway + workers in the background
omni status   # worker health as a table
omni doctor   # what works and what to fix, changing nothing
omni down     # stop everything, leave no orphans

API

Your existing OpenAI client works

Change one base_url and every OpenAI-shaped endpoint follows. Where OpenAI has no shape, omni invents a small, consistent one.

python
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:10000/v1", api_key="local")

# chat — streams, uses the configured chat model
client.chat.completions.create(
    model="qwen2.5:0.5b",
    messages=[{"role": "user", "content": "Summarise this ticket."}],
)

# embeddings — "embed" means the configured embed model
vectors = client.embeddings.create(model="embed", input=["refund policy"])

# image — returns base64 PNG
client.images.generate(model="image", prompt="a lighthouse at dawn", size="1024x1024")

# speech — a wav on disk
client.audio.speech.create(model="tts", voice="af_heart", input="Hello from omni.").write_to_file("out.wav")
shell
# chat (streaming)
curl -N localhost:10000/v1/chat/completions -H 'content-type: application/json' \
  -d '{"messages":[{"role":"user","content":"Say hi"}],"stream":true}'

# embeddings — input_type is "query" or "document"
curl localhost:10000/v1/embeddings -H 'content-type: application/json' \
  -d '{"input":"how do I get a refund?","input_type":"query"}'

# image -> png
curl localhost:10000/v1/images/generations -H 'content-type: application/json' \
  -d '{"prompt":"a lighthouse at dawn","size":"1024x1024","steps":20}' \
  | jq -r '.data[0].b64_json' | base64 -d > out.png

# health
curl localhost:10000/health
json
curl localhost:10000/v1/systemone -H 'content-type: application/json' -d '{
  "state": "I have asked three times and still no refund!",
  "questions": {
    "is_frustrated": {"type": "noul", "instructions": "Does the customer sound frustrated?"},
    "topic": {"type": "choice", "instructions": "What is this about?",
              "criteria": {"billing": "money, refunds", "shipping": "delivery"}}
  }
}'

# noul, choice and score answers come back with calibrated
# probabilities per option — no generated text to parse
shell
# text to speech -> wav
curl localhost:10000/v1/audio/speech -H 'content-type: application/json' \
  -d '{"input":"Hello from omni.","voice":"af_heart"}' -o hello.wav

# speech to text — json | text | verbose_json
curl localhost:10000/v1/audio/transcriptions \
  -F file=@hello.wav -F response_format=verbose_json

# video — create a job, poll it, fetch the mp4
curl localhost:10000/v1/videos -H 'content-type: application/json' \
  -d '{"prompt": "a paper boat in the rain", "size": "704x480", "seconds": 4}'
curl localhost:10000/v1/videos/video_abc123
curl localhost:10000/v1/videos/video_abc123/content -o clip.mp4

Every endpoint, including the admin routes, answers errors as {"error": {"message": "...", "type": "..."}}.

FAQ

Questions people actually ask

Does anything leave my machine?

No. omni binds to 127.0.0.1 and talks to local engines over Unix sockets. The only network traffic is the first model download from Ollama or Hugging Face. A non-loopback --host is refused unless you set OMNI_ALLOW_NON_LOOPBACK=1.

Do I need to install a server for every model?

No. omni init installs Ollama when it is missing and pulls the models you need. The Python roles — image, video, speech — run inside omni's own workers, each in its own process.

What happens when a model crashes?

The supervisor health-checks every worker every two seconds and restarts a failed one with exponential backoff. A worker stuck starting for 120 seconds is restarted too. One role going down never takes the others with it.

Is the first request slow?

Yes — it loads the model, and some roles download on first use. Pin the roles you use often and they stay loaded: omni re-loads them before they would idle out, and pins persist across restarts.

Can I use it with my own app?

Point any OpenAI client at http://127.0.0.1:10000/v1 and change base_url. Roles that OpenAI does not model — decide, video — have their own small endpoints with the same error shape.

Which platforms are supported?

macOS on Apple Silicon runs every role. Linux serves chat, decide and embed through Ollama, and adds speech and video with the media extra. The image worker renders on Metal, so it stays macOS-only.
